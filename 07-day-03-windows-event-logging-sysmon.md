## What I Learned

### 1. Windows Logging Architecture

Windows maintains five core logs, each serving a distinct purpose:

| Log                | Purpose                                                                                  |
| ------------------ | ---------------------------------------------------------------------------------------- |
| Application        | Events logged by applications (default destination for application-reported events).      |
| Security           | Audit events generated by the OS (logons, object access, policy changes).                 |
| Setup              | Events related to OS installation and service pack / update installation.                |
| System             | Events logged by Windows system components and drivers.                                   |
| Forwarded Events   | Events forwarded from other machines (used in centralised SIEM collection).              |

The event flow is: **Application -> Windows Event Log Service -> Log Channel -> `.evtx` file -> Event Viewer**. Each `.evtx` file is a structured binary container that Event Viewer renders into human-readable form on demand.

### 2. Security Auditing Concepts

Windows Audit Policies (configured via `secpol.msc`) determine what gets logged to the Security log. Key Security Event IDs documented during the session:

| Event ID | Meaning                                                                |
| -------- | ---------------------------------------------------------------------- |
| 4624     | An account was successfully logged on                                   |
| 4625     | An account failed to log on                                            |
| 4720     | A user account was created                                             |
| 4732     | A member was added to a security-enabled local group                    |
| 1102     | The audit log was cleared                                               |

Event ID 1102 is particularly high-signal: clearing the audit log outside of approved maintenance windows is a classic defense-evasion technique that should trigger immediate review.

### 3. Sysmon Installation & Configuration

Sysmon was downloaded along with the SwiftOnSecurity community configuration from GitHub. Initial installation hit two issues:

1. **Missing config file** - the configuration XML was not in the working directory where `Sysmon64.exe` was invoked.
2. **Incorrect working directory** - PowerShell was launched from a path that didn't contain the Sysmon binary, requiring `cd` to the correct location.

After resolving these, Sysmon was successfully installed:

```powershell
Sysmon64.exe -accepteula -i sysmonconfig-export.xml
```

Sysmon logging was verified active under: **Applications and Services Logs -> Microsoft -> Windows -> Sysmon -> Operational**.

### 4. Test Event Generation & Analysis

A successful logon Event ID 4624 was triggered by locking and unlocking the workstation. Event fields reviewed in Event Viewer:

- Logon Type (2 = Interactive, 7 = Unlock, 10 = RemoteInteractive)
- Account Name
- Process Name (the logon process that initiated the session)
- Logon GUID (correlates with Kerberos ticket events in other logs)

### 5. PowerShell `Get-WinEvent` & Structured XML

Using `Get-WinEvent` to pull provider templates and raw XML for Event ID 4624 revealed the underlying structure of a Windows event:

- **System XML** - contains EventID, TimeCreated, Provider Name, Channel, Level, Computer.
- **EventData XML** - contains the event-specific payload (TargetUserName, LogonType, ProcessName, etc.).
- **Manifest Template** - the provider's message template that Event Viewer uses to render the human-readable message.

The key insight: **structured XML is preferred for automated/SIEM parsing over plain-text messages**. The rendered message can change with locale or Windows version, but the XML schema is stable. SIEM platforms (Splunk, Wazuh, ELK) ingest the XML fields directly and build their detection logic on field names, not on string matching against rendered messages.

```powershell
# Example: pull raw XML for a specific event
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624} -MaxEvents 1 |
    Select-Object -ExpandProperty ToXml
```
